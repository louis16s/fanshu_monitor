# 极端负载与资源占用审查

日期：2026-10-17；版本：0.3.4；平台：macOS 27 / Apple Silicon

## 结论与范围

检查了模块采样调度、鼠标输入、显示器发现与写入、DDC 超时、Gamma 生命周期、锁屏调度、Codex 网络与会话读取、设置持久化和动画启停的主要运行路径。本次修复三处负载保护缺口，保留现有刷新周期。

测试可以验证软件层的排队、取消和状态恢复；无法证明任意硬件驱动永久阻塞、任意体积文件、所有睡眠拓扑组合下都能保持固定 CPU 或内存上限。

## 已修复问题

### 1. High：慢速显示器写入仍可能形成长队列

- 位置：`FanshuMonitorDisplay/DisplayControlWorker.swift`，原 `perform` 与 `scheduleCoalescedWrite`
- 证据：滑杆防抖到期后直接向设备串行队列追加闭包；硬件写入慢于输入时，尚未执行的写入仍会不断增长
- 修复：滑杆与键盘使用同一写入入口；每个设备控制项保留一个在途写入和一个最新待写值，替换已经过时的中间值
- 验证：阻塞首笔写入，注入并强制提交 1,000 次滑杆更新，最终仅实际写入首值与末值；混合键盘/滑杆、睡眠取消、跨设备隔离测试继续通过
- 行为影响：忙碌期间过时的中间亮度值可以跳过，最终用户指定值保留

### 2. Medium：密集拓扑刷新会积累重复完成回调

- 位置：`FanshuMonitorDisplay/DisplayControlController.swift:refreshAsync`
- 证据：worker 合并硬件扫描，但会保存每个调用方的 completion；控制器原先没有限制自己注册回调的数量
- 修复：控制器只保留一个在途探测和一次待刷新标记；完成后按最新需求补一次；休眠或停止显示器服务时不继续补探测
- 验证：编译、静态分析与已有发现合并、睡眠恢复测试；本次未执行真实显示器连续插拔实验

### 3. Medium：会话文件巨大增量可能在一次刷新中全部解析

- 位置：`FanshuMonitor/CodexTaskProgressReader.swift:update`
- 证据：分块读取控制单块内存，但原循环会持续读取到文件当前末尾，没有单次增量预算
- 修复：每个 rollout 每次最多继续读取 2 MiB；保留字节偏移和跨块记录，下次刷新继续
- 验证：活跃任务追加超过 6 MiB 数据和终止事件，分四次读取后正确结束任务；跨块 UTF-8、超大记录和文件截断相关测试继续通过
- 行为影响：超大增量期间任务状态可能延后若干次刷新才追上文件末尾；正常小增量仍在当次刷新处理

## 现有保护检查

| 模块 | 代码中已有的保护 | 边界 |
| --- | --- | --- |
| CPU / GPU / UMA / Power | 独立 worker、取消与代次检查；面板关闭时保留菜单栏所需的降频采样 | 同步内核调用不能靠 Swift Task 取消强行中断 |
| 鼠标快捷键 | 后台串行执行、最多 8 个待处理动作、按下去重、修饰键释放、监听超时停止接管 | 拒绝事件风暴中的额外动作；真实鼠标故障仍需硬件验证 |
| DDC | 3 秒通信等待超时、按设备隔离、隔离冷却与有限恢复次数 | 超时不会终止已经卡在驱动中的系统调用 |
| 锁屏 | 单个锁定任务、有限确认轮询、重试间隔、睡眠与策略变更取消 | 私有登录 API 与真实登录窗口行为需实机复验 |
| Codex 额度 | 合并在途请求、12 秒网络超时、15/30/60 秒失败退避、失败保留成功值 | 网络超时并不等于响应体字节数硬上限 |
| Codex 活动任务 | 面板关闭时停止读取、最多 12 个候选与 256 个标题、单条记录限制 | 初始生命周期搜索仍可扫描每文件最多 16 MiB |
| 持久化与动画 | 主要高频遥测保留内存值；设置与恢复数据比较后写入；动画按可见性/减少动态效果启停 | 不能从短时零写入推导整天零写入 |

## 继续改进项

1. Medium：会话目录发现仍遍历整个目录树，标题索引初次读取/补查也可能扫描完整索引。极大历史库仍会产生读盘高峰。位置：`CodexTaskProgressReader.discoverRecentRollouts`、`updateSessionTitles`、`recoverMissingTitles`。后续应采用可恢复索引扫描和实测大历史库基准，兼顾旧会话标题与低开销。
2. Low：鼠标连接检测实际使用 5 秒定时枚举，不是旧架构文档声称的纯设备通知。已校正文档；迁移到长期 IOHID 订阅需要用当前鼠标验证蓝牙重连和权限变化。
3. Low：显示器 worker 的设备队列字典按运行期 display ID 保留。长期出现大量不同 ID 时，可进一步清理已经退休且无在途任务的队列，必须同时防止同一设备重连产生并行写入。

## 验证与测量

- 全量测试 331 项通过、0 项失败；Release 静态分析、Release 构建、签名与启动检查通过，验证日志无编译警告
- 新增压力实验使用模拟硬件闭包及临时会话文件，没有向真实显示器写入 1,000 次亮度
- 修复前自然运行状态的 10 秒进程级采样：平均 CPU 0.011%，physical footprint 70.110 MiB，进程统计磁盘读写增量均为 0 字节
- 新版启动后两个连续 10 秒窗口：平均 CPU 分别 0.023% / 0.013%，physical footprint 分别 18.860 / 18.876 MiB，两个窗口进程磁盘读写增量均为 0 字节；另测 RSS 约 80 MiB、线程数 6
- RSS 与 physical footprint 的共享页面计账口径不同；重启也会改变缓存和界面驻留状态，因此不能把前后内存差异直接归因于本次修改
- 上述读写来自 `proc_pid_rusage`，不是整机磁盘统计，也不包括 cfprefsd 等系统代理进程代写的数据
- 没有自动切换用户的面板状态；自然运行测量不能代替面板全展开、真实多屏、低电量和持续数天运行的测试

建议真实硬件复验：连续复制/粘贴、多显示器各自调亮度、外屏重启与快速拔插、睡眠唤醒后重新登录、撤销/重新授权输入权限，以及 24–72 小时运行。
